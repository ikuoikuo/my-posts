## TL;DR
- サンプルのECサイトにRedisを導入し、パフォーマンス改善効果を検証した
- Redisによるキャッシュ活用でPostgreSQLへのアクセスを削減した
- DB接続待ちが減少し、より多くのリクエストを処理できるようになった
- Redisにはキャッシュ以外の用途もあるが、本記事ではキャッシュ利用に焦点を当てる

## 1. Redis とは
**Redis**は、キー/バリュー型を中心とした多様なデータ構造を扱えるオープンソースのインメモリデータストアです。
Redisは極めて高速なインメモリデータストアとして知られており、この高速性は、すべてのデータをディスクではなくメモリ上に保存・提供するという特性に由来します。

従来のRDBMS（PostgreSQL、MySQLなど）はデータをディスクに保存するため、読み書きのたびにディスクI/Oが発生します。インメモリDBはデータを**メモリ上**に保持するため、このI/Oが発生せず、より速く応答できます。

## 2. Redis 導入ストーリー
今回は自作のサンプルECサイトにRedisを導入し、その効果を検証してみます。

このシステムでは、商品閲覧と予約処理の両方が在庫情報を管理するInventory DBへアクセスします。アクセス数が増加すると、DBコネクションプールが枯渇し、リクエストが接続待ちとなる可能性があります。

そこで、閲覧処理で何度も参照される在庫情報をRedisに保存し、DBの代わりにRedisから取得できるようにします。

頻繁に参照されるデータをRedisから取得できるようになれば、DBへのアクセス回数を削減でき、結果としてDB接続待ち時間の短縮や応答性能の向上が期待できます。

### Redis 導入前の構成
商品閲覧や予約処理のすべてがDBへ直接アクセスする構成です。
アクセスが集中するとDB負荷が増大し、接続待ちが発生することでレスポンス遅延につながります。
![image.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/3086181/cb235af2-b2e8-47d6-9eb1-6b165f142a29.png)

> 構成図は最近流行りの[archify](https://github.com/tt-a1i/archify) を用いて作成しました。

### Redis 導入後の構成
Inventory ServiceはまずRedisへ問い合わせを行います。

キャッシュにデータが存在する場合はRedisから応答を返し、DBへのアクセスは発生しません。キャッシュに存在しない場合のみDBへ問い合わせます。

この構成により、

- レスポンス時間の短縮
- DB負荷の軽減
- DB接続待ち時間の削減

が期待できます。

![image.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/3086181/b54761be-dd7e-41d3-94f4-886dc74d7b68.png)


> このようなサンプルアプリケーションを1つ持っておくと、新しいミドルウェアやアーキテクチャを気軽に試せるため非常に便利だと感じています。

## 3. パフォーマンス比較
以下の6指標を用いて比較を行いました。各指標の説明は以下のとおりです。
負荷テストには k6 を使用しています。シナリオの詳細は割愛しますが、アクセスが段階的に増加し、ピークが2回発生するような負荷パターンを設定しています。

| 指標              | 説明                        
| --------------- | -------------------------- 
| DBオペレーション/リクエスト | 1リクエストあたりに発生したDBアクセス回数    |
| p95レイテンシ        | 全リクエストの95%が収まる応答時間         | 
| リクエスト数          | システムに送信されたリクエスト数           |
| 空プール待ち時間        | DBコネクションプールに空きがなく、接続を待った時間          |
| 1acquireあたり待ち時間 | DBコネクション取得1回あたりの平均待機時間     | 
| 接続数             | DBコネクションプールの使用状況           |

### Redis 導入前後のメトリクス比較
Grafana を用いて Redis 導入前後のメトリクスを比較しました。黄色が Redis 導入前、緑が Redis 導入後を表しています。

 ![image.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/3086181/345e1696-95ad-4f97-ba1a-d9e1f41944a0.png)
 
グラフから、Redis導入後は**1リクエストあたりのDBオペレーション数**が減少していることが確認できます。また、Redis導入前に発生していた**コネクションプールの接続待ち**もほぼ解消されており、DB負荷が軽減されていることが分かります。

一方で、**p95レイテンシ**には大きな差は見られませんでした。今回の負荷条件ではもともとのレイテンシが低く、DB待ち時間が支配的なボトルネックではなかった可能性があります。
 
ただし、同程度のレイテンシを維持しながら、Redis導入後の方が1秒あたりに処理できる**リクエスト数**は増加しており、システムの処理効率は向上していると考えられます。

## 4. まとめ
Redisをキャッシュ層として導入したことで、 DBへのアクセス回数を削減し、 接続待ち時間の減少やスループット向上を確認することができました。
なお今回初めてRedisを使用してみましたが、キャッシュ以外にも、セッション管理などさまざまな用途で利用できるらしいので、それらは別の機会に試してみたいと思います。
